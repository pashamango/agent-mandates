## 1. Проблемы, которые решает версия vNext

1. **Рост очереди задач agy при pacing 300с**:
   * Ограничение pacing (минимум 300 секунд между запусками agy) необходимо для защиты от скользящей 10-часовой квоты (`Individual quota reached`). Однако при всплеске задач ВС/ВП очередь растёт: задачи Collatz [MIN-219](https://linear.app/mindrock/issue/MIN-219) и [MIN-221](https://linear.app/mindrock/issue/MIN-221) ожидали подхвата более 2 часов (дозор 09:41, 25.10).
2. **Слот codex-local не подтверждён как живой билдер**:
   * Слот codex в демоне `fleetd` сконфигурирован, но старая цепочка `codex@wolfram` признана мёртвой 22.10. Задача MIN-221 была заявлена за codex-on-Wolfram, но по факту сборку выполнял agy. Fallback на codex без health-check опасен.
3. **Опасность текстового regex-матчинга `Builder:` без word boundary**:
   * В текущем поллере маркер `Builder: codex-cloud` ошибочно матчился как локальный `codex`, вызывая конфликты и двойные захваты ([MIN-124](https://linear.app/mindrock/issue/MIN-124), [MIN-173](https://linear.app/mindrock/issue/MIN-173)).
4. **Утечка вычислительной квоты на низкоценные циклы**:
   * Полировка уже отправленных заявок (тир МП после submission: [MIN-213](https://linear.app/mindrock/issue/MIN-213), [MIN-222](https://linear.app/mindrock/issue/MIN-222)) продолжалась после отправки, расходуя драгоценную квоту без изменения внешнего исхода.

## 2. Цели версии (WHAT)

1. **Автономная маршрутизация**: `fleetd` самостоятельно маршрутизирует задачи между лейнами `agy` и `codex-local` на основе тиров, времени ожидания и квот, а не отдаёт случайную задачу.
2. **Детерминированный гейт канона**: `fleetd` валидирует задачи от PM перед выдачей билдеру; неканоничные задачи не берутся в работу, а немедленно возвращаются PM со статусом `REWORK`.
3. **Версионируемое обучение по Ledger**: решения маршрутизации логируются в `routing_ledger.jsonl`; обновление политики проходит регрессионный тест на исторических инцидентах; запрещены скрытые онлайн-мутации.
4. **Защита замороженного ядра (Frozen Core)**: тапы Павла, QA-гейты, правило `END != DONE`, запрет на подмену моками или старым python-диспетчером остаются абсолютными инвариантами.

## 3. Архитектура маршрутизации

### 3.1 Лейны и их специализация

* **`agy` (основной лейн)**:
  * MacBook Wolfram, агент NICLI-режима.
  * Pacing: жесткий интервал $\ge 300$ секунд между запусками (`AGY_MIN_INTERVAL_SECS`).
  * Сфера: ядро архитектуры, математические доказательства (MathLab / Lean 4), полные сборки.
* **`codex-local` (fallback-лейн)**:
  * MacBook Wolfram, слот `codex` в `fleetd`.
  * Fallback-лейн: активируется **только** после прохождения health-check (§6).
* **`codex-cloud` (внешний изолированный лейн)**:
  * Облачный лейн ChatGPT/Codex.
  * Захват только по `assignee: Codex` + `@Codex`-упоминанию.
  * Локальный `fleetd` **никогда не захватывает** задачи облачного лейна.

### 3.2 Единый орган захвата (Single-Lease Protection)

* Захват задачи осуществляется исключительно `fleetd`.
* Каждому активному захвату соответствует неизменяемая запись аренды (Lease Record):
  ```json
  {
    "task_id": "MIN-229",
    "slot": "agy",
    "lease_timestamp": 1792948800,
    "lease_ttl_secs": 3600,
    "handoff_git_commit": "09dd8b49cd28c20d2a1e0dfb50ad2e8924e53e75"
  }
  ```
* **Защита от двойного захвата**: попытка второго слота взять задачу с активным lease отклоняется с кодом `DOUBLE_CLAIM_REJECTED` и заносится в ledger как инцидент.
* Маркер `Builder:` в тикете — это подсказка (hint), а решение о назначении принимает `fleetd`.

### 3.3 Правило триггера Fallback

Fallback на `codex-local` разрешён **только при одновременном выполнении четырёх условий**:
1. Слот `codex-local` имеет статус `HEALTH_OK` по результатам health-check.
2. Тир задачи — **строго ВС или ВП** (задачи МС и МП в fallback не переводятся).
3. Задача находится в статусе `Todo` без подхвата `agy` **более 2 часов (7200 с)** ИЛИ получен явный сигнал исчерпания квоты `agy` (`429 Resource Exhausted`).
4. В слоте `codex-local` выполняется **не более одной задачи одновременно** ($\text{WIP}_{\text{fallback}} \le 1$).

Как только `agy` возвращается к штатной разборке задач в пределах pacing, fallback-захваты прекращаются.

### 3.4 Квоты и Pacing — Fail-Closed

* Каждый слот ведет независимый учет квоты и pacing.
* При получении сигнала `RESOURCE_EXHAUSTED` (HTTP 429) слот переводится в состояние `QUOTA_EXHAUSTED` до истечения указанного TTL. Запрещено молча перебрасывать задачи остановленного слота на другой слот.
* **Защита пула QA**: локальный Codex и облачный QA используют общий лимит ChatGPT. Fallback-кап гарантирует резерв квоты для независимого QA. Задержка QA ради билда недопустима.
* Проверка результатов билда всегда выполняется **независимым лейном** (перекрёстный аудит `agy` $\leftrightarrow$ `codex`).

## 4. Проверка канона: задача без проекта — REWORK

Перед выдачей задачи билдеру модуль `canonical_gate` выполняет 4 детерминированные проверки. Если хотя бы одна нарушена — задача **не выдаётся билдеру**, статус в Linear переводится в `In Progress` с комментарием REWORK к PM:

1. **Проект обязателен (Project Mandatory)**:
   * Задача обязана иметь привязку к проекту в Linear (`issue.project != null`).
   * Нарушение: отказ с сообщением `REWORK: Задача не привязана к Linear Project. Укажите проект-контейнер.`
2. **Тир обязателен (Tier Mandatory)**:
   * Описание задачи обязано содержать явный маркер: `Tier: ВС`, `Tier: ВП`, `Tier: МС` или `Tier: МП`.
   * Нарушение: отказ с сообщением `REWORK: Отсутствует классификация тира (Tier: ВС/ВП/МС/МП).`
3. **Submitted = Frozen**:
   * Задача тира `МП` (поданная заявка / submission) блокируется для билдера после отправки.
   * Исключение: явная пометка в тикете о запросе рекрутера или обнаружении материальной ошибки.
4. **Маркерная дисциплина (Strict Word-Boundary Matching)**:
   * Поиск маркера билдера выполняется строго по границам слов: `\bBuilder:\s*(agy|codex)\b`.
   * Маркеры вроде `Builder: codex-cloud` распознаются как внешний облачный лейн и локальным демоном игнорируются. Неоднозначные маркеры возвращаются PM на исправление.

## 5. Умный fleetd: Локальная модель как мозг маршрутизации

### 5.1 Разделение полномочий

| Компетенция | Решает локальная модель? | Детерминированное ядро / Человек |
|---|---|---|
| Выбор оптимального слота (`agy` vs `codex-local`) | ✅ ДА | — |
| Очередность и приоритет разбора внутри очереди | ✅ ДА | Детерминированный fallback |
| Тап на релиз проекта (`Done`) | ❌ НЕТ | Только Принципал Павел Черкашин |
| Вердикт QA (`PASS` / `REWORK`) | ❌ НЕТ | Независимый QA-агент |
| Смена тира задачи | ❌ НЕТ | Только PM / Принципал |
| Правила канона (§4) | ❌ НЕТ | Детерминированный гейт `canonical_gate` |

### 5.2 Контракт локальной модели (Wolfram Offline Model Contract)

* **Автономия:** Модель работает локально на Wolfram, офлайн, без внешних платных API в горячем цикле.
* **Аппаратный бюджет Wolfram:** 16 GB RAM, $\ge 20$ GB свободного диска. Модель с квантованием (например, Qwen2.5-Coder-1.5B/3B Q4_K_M через llama.cpp или mlx) занимает $\le 2.5$ GB RAM.
* **Бюджет времени:** Решение принимается $\le 3$ секунд.
* **Fail-Closed Fallback:** Если модель недоступна, зависла или превысила таймаут 5с, `fleetd` мгновенно переходит на **детерминированные правила** (§3–§4), логирует инцидент `MODEL_ROUTER_UNAVAILABLE` в ledger и продолжает непрерывную работу.

### 5.3 Routing Ledger и версионируемое обучение

Каждое решение маршрутизатора сохраняется в `fleetd-evolution/data/routing_ledger.jsonl`:
```json
{
  "timestamp": "2026-10-25T18:40:00Z",
  "task_id": "MIN-229",
  "tier": "ВП",
  "wait_time_secs": 180,
  "chosen_slot": "agy",
  "router_mode": "model_offline_fallback_rule",
  "active_leases": {"agy": "MIN-229", "codex": null},
  "quota_status": {"agy": "OK", "codex": "OK"},
  "canonical_check": "PASS",
  "outcome": "IN_PROGRESS"
}
```

* **Обучение на ошибках**: Обновление эвристик модели и политик маршрутизации выполняется пакетами (batch), с фиксацией версии политики (например, `policy_v1.0.json`).
* **Регрессионный тест на исторических инцидентах**:
  * MIN-124 & MIN-173: Защита от захвата `codex-cloud`.
  * MIN-213 & MIN-222: Блокировка submitted MP-задач.
  * MIN-221 & MIN-219: Своевременный fallback при задержке $>2$ часов.
* Если новая версия политики допускает хотя бы один регресс по сравнению с базовой, выполняется немедленный **Rollback** к детерминированным правилам.

## 6. Пилот перед включением Fallback

Fallback-лейн для всей очереди остаётся заблокирован до выполнения трёх условий:

1. **Health-Check слота `codex-local`**:
   * Проверка запуска исполняемого файла codex.
   * Проверка генерации корректного handoff-отчёта по протоколу Git.
2. **Пилотная задача [MIN-221](https://linear.app/mindrock/issue/MIN-221) (Collatz M3)**:
   * Входные данные: тир ВП, содержательный FAIL по проверке сложности чекера.
   * Исполнение в слоте `codex-local`.
   * Сдача: воспроизводимый git-handoff (`repo_url`, `branch`, точный `commit_sha`).
   * Валидация независимым QA в чистом окружении.
3. **Активация**:
   * Только после получения `PASS` от независимого QA по пилоту MIN-221 fallback переводится в боевой режим.
